# ruletka.top — Environment Variable Checklist & Audit

> **What this is.** An accurate, code-verified inventory of every environment
> variable the platform reads, grouped by service, with where each value comes
> from and whether the deploy tooling actually provides it. Every variable name
> below was found by grepping the real source — none are invented.
>
> **Sources audited** (all paths relative to the repo root):
>
> - `apps/api` (NestJS) — every `ConfigService.get(...)` and `process.env.*`.
> - `apps/web` (Next.js 16) — every `process.env.NEXT_PUBLIC_*` and other `process.env.*` in `src/` + config files.
> - `apps/admin` (Vite React SPA) — `import.meta.env.VITE_*`.
> - `infra/docker/docker-compose.prod.yml` — `build.args` + `environment` blocks.
> - `infra/deploy/bootstrap.sh` — the `.env` heredoc and the `NEXT_PUBLIC_*` build args it forwards (it now also generates the Mongo auth secrets + replica-set keyFile and an auto `METRICS_TOKEN`), **plus a self-healing `upsert_env` pass that runs on every deploy** (not just the first) so a key newly required by the code lands on already-deployed servers without operator intervention. Today's failure class — `METRICS_TOKEN` + `MONGO_*` missing from an older `.env` — cannot recur.
> - `.env.example` (repo root) — documented vs. actually-used.
>
> **Status legend**
>
> - ✅ **wired** — read in code **and** generated by `bootstrap.sh` (or injected by compose). Works out of the box.
> - ⚠️ **gap (code, not bootstrap)** — read in code but **NOT** written by `bootstrap.sh`. On a fresh server it is simply _unset_ → the feature stays in its no-op/default state until you add it to `.env` by hand. **These are the features that silently stay OFF.**
> - 🟡 **optional default** — read in code with a safe built-in default; absence is intentional and harmless.
> - 🔴 **set-but-unused** — written by bootstrap / documented in `.env.example` but **never read by code**. Dead config — harmless but misleading.
> - 🧩 **infra/compose** — provided by `docker-compose.prod.yml` (env or build-arg), not by the `.env` heredoc.
>
> **How `.env` works here (important):** `bootstrap.sh` generates `/opt/ruletka/.env`
> **once** (full heredoc) and never overwrites EXISTING values. **On every subsequent
> run** it executes a `upsert_env KEY VALUE` self-heal pass that ADDS any
> code-required secret that's currently missing or blank — `METRICS_TOKEN`,
> `MONGO_ROOT_USERNAME`/`MONGO_ROOT_PASSWORD`, `MONGO_APP_USERNAME`/`MONGO_APP_PASSWORD`,
> and a canonical `MONGODB_URI` rebuild when the URI is empty or still uses the
> dev `directConnection` format. Existing operator-supplied values (Turnstile,
> T-Bank, Sightengine, SMTP_PASS) are **never** touched.
>
> **The operator therefore only ever supplies the secrets they alone hold**
> (Turnstile, T-Bank, Sightengine, SMTP password — see `SECRETS-INSTALL.md`).
> Everything else is auto-generated and self-heals across deploys.
>
> To change a value later you edit `.env` in place. The repo's documented pattern is:
>
> ```bash
> cd /opt/ruletka
> sed -i '/^KEY=/d' .env && echo 'KEY=value' >> .env
> ```
>
> Then:
>
> - **API-only vars** → restart the API: `docker compose --env-file .env -f infra/docker/docker-compose.prod.yml up -d --no-deps api`
> - **`NEXT_PUBLIC_*` (web) vars** → these are **baked into the web bundle at build time**, so you must **rebuild** the web image: re-run `bash infra/deploy/bootstrap.sh` (or `… up -d --build web`). A restart alone does nothing.

## 🔴 TL;DR — the gaps that matter most

1. **Coin & premium payments ship OFF.** All four CloudPayments vars
   (`CLOUDPAYMENTS_PUBLIC_ID`, `CLOUDPAYMENTS_API_SECRET`,
   `CLOUDPAYMENTS_WEBHOOK_IPS`, `NEXT_PUBLIC_CLOUDPAYMENTS_PUBLIC_ID`) are read by
   code and documented in `.env.example`, but **`bootstrap.sh` does not generate
   them**. A fresh deploy has an empty Public ID and an empty webhook secret, so
   the payment flow cannot complete (details in the dedicated section below). →
   **You must add these by hand.**

2. **`ARGON2_MEMORY_COST` / `ARGON2_TIME_COST` are 🔴 set-but-unused.**
   `bootstrap.sh` writes them (lines 107–108) and `.env.example` documents them
   (lines 35–36), but the password hasher uses **hard-coded constants**
   (`apps/api/src/modules/auth/auth.service.ts:114-115`: `memoryCost: 19_456,
timeCost: 2`). Editing these env vars has **no effect**. Either wire them or
   drop them from bootstrap/.env.example.

3. **Client-side AI moderation vars are unreachable in prod.**
   `NEXT_PUBLIC_NSFW_MODEL_URL`, `NEXT_PUBLIC_MOD_THRESHOLD_NUDITY`,
   `NEXT_PUBLIC_MOD_THRESHOLD_SEXUAL`, `NEXT_PUBLIC_MOD_SAMPLE_MS` are read in
   `apps/web/src/features/moderation/*`, but they are **missing from
   `docker-compose.prod.yml`'s `web.build.args`** _and_ from bootstrap. Because
   `NEXT_PUBLIC_*` must be passed as a Docker build-arg to be baked in, these can
   **never** be set on the current prod build without editing the compose file.
   They fall back to code defaults (thresholds 0.85 / 0.7, bundled model URL).

4. **Several API integrations are gap (code, not bootstrap)** — they default to a
   clean no-op, so this is "optional but undiscoverable from `.env`":
   `FIREBASE_SERVICE_ACCOUNT` (mobile push),
   `FRAME_SCORER` + `MODERATION_PROVIDER_API_KEY` + `SIGHTENGINE_*` (server
   moderation), `PRESENCE_TTL_SECONDS`, `THROTTLE_LIMIT`, `AUTH_THROTTLE_LIMIT`,
   `FINGERPRINT_BAN_ENABLED`, and the server-side Sentry tunables
   (`SENTRY_TRACES_SAMPLE_RATE`, `SENTRY_PROFILES_SAMPLE_RATE`, `SENTRY_ENV`, …).
   (`METRICS_TOKEN` used to be in this list — it is now **auto-generated by
   bootstrap** because the API fails-fast on a blank one in prod.)

5. **Prod Mongo now runs with AUTH (`--auth --keyFile`).** `bootstrap.sh`
   generates the replica-set keyFile (`infra/secrets/mongo-keyfile`) + a root
   password + a least-privilege `app` password, and builds a credentialed
   `MONGODB_URI`. Previously the RS ran unauthenticated (Docker-network isolation
   only). The new secrets are listed in the **Mongo / Redis** reference below.

**Counts:** API reads **~48** distinct vars; Web reads **~24** real `NEXT_PUBLIC_*`/build vars; Admin reads **1** (`VITE_API_URL`); Infra/compose contributes Mongo/Redis/TURN wiring. Total distinct platform vars catalogued below: **~70**.

# 💳 Enable coin payments (CloudPayments)

**Out of the box, payments are OFF** — `bootstrap.sh` does not generate any
CloudPayments variable, so a fresh server has an empty Public ID and an empty
webhook secret.

### The exact vars that switch payments on

| Layer              | Variable                              | What it does                                                                                                                                                                                                           | Where to get it                                                             |
| ------------------ | ------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------- |
| **Web (coins)**    | _(none — server-supplied)_            | The **coins** widget uses the Public ID the API returns from `POST /payments/coins/checkout` (`params.publicId`, see `features/coins/use-coins.ts:86`). That value comes from the **API's** `CLOUDPAYMENTS_PUBLIC_ID`. | —                                                                           |
| **Web (premium)**  | `NEXT_PUBLIC_CLOUDPAYMENTS_PUBLIC_ID` | The **premium** recurrent widget builds params **client-side** and needs the Public ID baked into the bundle (`features/premium/use-premium.ts:27`).                                                                   | CloudPayments **merchant dashboard → Site settings → Public ID**            |
| **API**            | `CLOUDPAYMENTS_PUBLIC_ID`             | Returned to the coins widget at checkout (`payments.service.ts:89`).                                                                                                                                                   | CloudPayments **dashboard → Site settings → Public ID** (same value)        |
| **API**            | `CLOUDPAYMENTS_API_SECRET`            | HMAC-SHA256 secret used to **validate every webhook** (`cloudpayments-signature.guard.ts:53,90`). This is what actually credits coins / activates premium.                                                             | CloudPayments **dashboard → API secret / password** (used for webhook HMAC) |
| **API (optional)** | `CLOUDPAYMENTS_WEBHOOK_IPS`           | Optional network allow-list for the webhook source IP (`cloudpayments-signature.guard.ts:55`).                                                                                                                         | CloudPayments' published notification IP ranges                             |

### Current behaviour when unset (confirmed from code)

- **`CLOUDPAYMENTS_PUBLIC_ID` empty** → `payments.service.ts:89` resolves to `''`,
  so the coins checkout returns an **empty `publicId`** and the CloudPayments
  widget cannot open a valid charge.
- **`NEXT_PUBLIC_CLOUDPAYMENTS_PUBLIC_ID` empty** → `use-premium.ts:27` →
  `CP_PUBLIC_ID = ''`; the premium recurrent widget has no merchant to bill.
- **`CLOUDPAYMENTS_API_SECRET` empty → FAIL-CLOSED.** The webhook guard logs
  `"CLOUDPAYMENTS_API_SECRET is not configured"` and throws **401
  Unauthorized** (`cloudpayments-signature.guard.ts:70-74`) **before** any HMAC
  work. So even if a user somehow paid, **no coins would ever be credited and no
  premium activated** until the secret is set. This is the single most important
  payment variable.

### Exact commands to enable it on the server

> `.env` lives at `/opt/ruletka/.env` and is generated **once**; edit it in place.
> `NEXT_PUBLIC_*` is baked at **build time** → the web image must be **rebuilt**.
> The API secret/public-id only need an **API restart**.

```bash
cd /opt/ruletka

# 1) Set the three CloudPayments values (idempotent: delete-then-append).
PUBLIC_ID='pk_xxxxxxxxxxxxxxxxxxxxxxxxx'      # CloudPayments → Site settings → Public ID
API_SECRET='your-cloudpayments-api-secret'    # CloudPayments → API secret (webhook HMAC)

# API-side (restart only):
sed -i '/^CLOUDPAYMENTS_PUBLIC_ID=/d'  .env && echo "CLOUDPAYMENTS_PUBLIC_ID=${PUBLIC_ID}"   >> .env
sed -i '/^CLOUDPAYMENTS_API_SECRET=/d' .env && echo "CLOUDPAYMENTS_API_SECRET=${API_SECRET}" >> .env
# Optional network allow-list:
# sed -i '/^CLOUDPAYMENTS_WEBHOOK_IPS=/d' .env && echo 'CLOUDPAYMENTS_WEBHOOK_IPS=1.2.3.4,5.6.7.8' >> .env

# Web-side (must be baked at build → set the build-arg value, then rebuild):
sed -i '/^NEXT_PUBLIC_CLOUDPAYMENTS_PUBLIC_ID=/d' .env \
  && echo "NEXT_PUBLIC_CLOUDPAYMENTS_PUBLIC_ID=${PUBLIC_ID}" >> .env

# 2) Apply.
COMPOSE="docker compose --env-file .env -f infra/docker/docker-compose.prod.yml"

# API: restart picks up the new secret + public id immediately.
$COMPOSE up -d --no-deps api

# Web: REBUILD so NEXT_PUBLIC_CLOUDPAYMENTS_PUBLIC_ID is baked into the bundle.
# (compose reads it as a build-arg at docker-compose.prod.yml:169.)
$COMPOSE up -d --no-deps --build web
# …or simply re-run the whole bootstrap, which rebuilds web with the new .env:
#   bash infra/deploy/bootstrap.sh
```

3. **In the CloudPayments dashboard**, point the **Pay / Recurrent notification
   webhooks** at `https://api.ruletka.top/api/payments/...` (the route the
   `CloudPaymentsSignatureGuard` protects) so charges call back and fulfilment
   runs.

> **Optional hardening:** `bootstrap.sh` does not generate these three keys, so
> they survive `git pull` + re-bootstrap (the `.env` is never overwritten). If you
> want them auto-seeded on fresh installs, add them to the heredoc — but that is a
> code change outside this audit.

# 🔐 MongoDB authentication (prod replica set)

**Out of the box now, the prod replica set runs AUTHENTICATED.** Previously the
3-node RS ran with `mongod --replSet rs0 --bind_ip_all` and **no `--auth`** — only
the isolated Docker network protected it. It now runs
`mongod --replSet rs0 --bind_ip_all --auth --keyFile /etc/mongo-keyfile`.

### What `bootstrap.sh` generates (all automatic — you supply nothing)

| Secret | Shape | Role |
| --- | --- | --- |
| `infra/secrets/mongo-keyfile` | `openssl rand -base64 756`, `chmod 400` | Shared **internal** auth so the 3 RS members trust each other. Bind-mounted read-only into all nodes + `mongo-init`. **Git-ignored** (`infra/secrets/`) — never commit it. |
| `MONGO_ROOT_USERNAME` / `MONGO_ROOT_PASSWORD` | `root` / `openssl rand -hex 24` | Mongo superuser. Created by each node's image entrypoint (`MONGO_INITDB_ROOT_*`, over the loopback localhost-exception). Infra-only; `mongo-init` uses it to `rs.initiate()` + create the app user. The API never uses root. |
| `MONGO_APP_USERNAME` / `MONGO_APP_PASSWORD` | `app` / `openssl rand -hex 24` | **Least-privilege** app user — `readWrite` + `dbAdmin` on the `ruletka` db **only** (no cluster/admin rights; `dbAdmin` is needed for `RUN_INDEX_SYNC`). The API connects as this user. |
| `MONGODB_URI` | `mongodb://app:<pw>@mongo1,mongo2,mongo3/ruletka?replicaSet=rs0&authSource=ruletka&retryWrites=true&w=majority` | The credentialed connection string. **Single source of truth in `.env`** — compose reads it via `${MONGODB_URI:?…}` (no longer hard-coded in compose). |

### How the auth bootstraps (order of operations)

1. Each mongo node's official-image entrypoint creates the **root** user from
   `MONGO_INITDB_ROOT_*` on first init (temporary loopback mongod → localhost
   exception), then re-execs the real `--replSet … --auth --keyFile` command.
2. `mongo-init` authenticates **as root** and runs `rs.initiate()`.
3. Once a PRIMARY is elected, `mongo-init` creates the least-privilege **app**
   user on the `ruletka` db. The API (`depends_on: mongo-init completed`) then
   connects as `app`.

It is **idempotent**: re-running bootstrap re-uses the existing keyFile, leaves
the already-initialised RS alone, and skips the app user if it already exists.

### Manual operations / recovery

```bash
cd /opt/ruletka
COMPOSE="docker compose --env-file .env -f infra/docker/docker-compose.prod.yml"

# Inspect users (authenticate as root; creds are in .env):
$COMPOSE exec -T mongo1 mongosh ruletka --quiet \
  -u "$(grep -E '^MONGO_ROOT_USERNAME=' .env | cut -d= -f2-)" \
  -p "$(grep -E '^MONGO_ROOT_PASSWORD=' .env | cut -d= -f2-)" \
  --authenticationDatabase admin --eval 'db.getUsers()'

# Rotate the APP password (root rotates it, then update MONGODB_URI + restart api):
# 1) changeUserPassword on the ruletka db, 2) sed the new pw into MONGODB_URI in .env,
# 3) $COMPOSE up -d --no-deps api
```

> ⚠️ The keyFile is part of each member's on-disk identity. **Do not regenerate
> it against existing `mongoN-data` volumes** — bootstrap only (re)creates it when
> it is missing. If you must rotate it, follow MongoDB's keyFile-rotation runbook
> (rolling restart), not a fresh `openssl rand`.

> **Using Atlas / external Mongo instead?** Set `MONGODB_URI` in `.env` to your
> managed connection string; the local mongo nodes + `mongo-init` + the keyFile
> become unused (you can stop those services). The `MONGO_*` vars are then inert.

> ⚠️ **Upgrading an EXISTING (previously unauthenticated) deployment.** The image
> creates the root user from `MONGO_INITDB_ROOT_*` **only on a fresh data dir**.
> A host whose `mongoN-data` volumes predate this change has **no** root user, so
> the nodes will start with `--auth` but `mongo-init` can't authenticate. Pick one:
>
> 1. **Create the users on the running (pre-auth) RS once, then enable auth.**
>    Before pulling this change, connect to the existing RS and create the same
>    `root` (admin db, role `root`) + `app` (ruletka db, `readWrite`+`dbAdmin`)
>    users with the passwords you'll put in `.env`; generate the keyFile; then
>    deploy. (MongoDB supports this via the `transitionToAuth` rolling pattern.)
> 2. **Or accept a data reset** if the prod data is disposable: stop the stack,
>    `docker volume rm ruletka-mongo{1,2,3}-data`, then bootstrap fresh.
>
> Fresh installs need none of this — the users are created automatically.
